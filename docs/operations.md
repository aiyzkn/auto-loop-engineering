# 運用の手引き

人とエージェントが、日々どう動くかをまとめます。エージェント向けの細かい手順は `skills/auto-loop/references/`、指令リポジトリの中の決まりは、そのリポジトリの `AGENTS.md` と `policy.md` にあります。

## 1. 人の動き

### 頼む

| 場面 | やり方 |
|---|---|
| PC の前にいる | Claude Code でそのまま頼む。複数ステップの作業なら、エージェントが起票してから着手する。どこまで進めてよいか（提案だけ / 実装まで / マージまで）を添える |
| 外出先・思いついたとき | 指令リポジトリの `inbox.md` に `## <案件>: <件名>` を足す（GitHub の画面で編集できる） |
| 急ぎ | 依頼に `優先: 緊急` と書く（会話なら「緊急で」と言う）。エージェントは、作業中のタスクを区切りで中断して先に行う。それ以外の依頼は、着手のたびに優先度を見比べて高いものから |
| 手が空いたときにしてほしいこと | `inbox.md` の「手が空いた時に実行するタスク」に `### <案件>: <件名>` で書いておく（段階・間隔・範囲）。着手できる依頼が無いときに、1 回に 1 件だけ行う |
| まとめて任せる | `inbox.md` に何件か書き、「受付を整理して、順に着手して」と頼む |

### 様子を見る

- 「ループの状態を見せて」（`/auto-loop status`）。人の対応が要るもの（`waiting`・`blocked`）が先に出る
- GitHub の画面で `projects/<案件>/tasks/` を開けば、タスクごとに「現在地」「成果物」「未確認・推測」が読める。コミットの履歴が、そのまま作業の記録になる

### 口を挟む

- 質問への回答は、タスクファイルの「利用者への質問と回答」に書く（会話で答えてもよい。エージェントが「決定事項」に記録する）
- 止めるときは `status: dropped` に書き換えるか、エージェントに伝える
- エージェントが止まったまま（上限・PC の故障）で、別のエージェントに続けさせたいときは、「`<タスク ID>` を引き継いで」と明示して頼む。エージェントは、指示なしには引き継がない

## 2. エージェントの動き（1 つのタスク）

```
intake → start（claim → preflight → 計画）→ 作業（checkpoint / delegate）→ finish → next
                                              ↑ 中断したら resume
next = 次にやることを 1 つ決める（再開 / 緊急への切り替え / 着手 / 手が空いたときの作業）
```

| 段階 | 要点 |
|---|---|
| 起票 | 原文をそのまま写す。段階の指定が無ければ「提案だけ」 |
| 着手 | push で担当を確定してから始める。認証・push 先・本流を先に確かめる。承認が要る操作を洗い出す |
| 作業 | 区切りごとに状態を記録する。判断待ちは `waiting` にして、依存しない部分を進める |
| 再開 | タスクファイルを正とする。前提（認証・サーバー・作業ツリー）を確かめ直す |
| 完了 | 実物で成果物の状態を確かめ、未確認を書き、報告して解放する |
| 次 | 着手のたびに優先度を判定しなおす。担当中のタスクは続けるのが原則で、緊急（`urgent`。利用者だけが指定する）は先に行う。同じ PC では、同時には 1 つのリポジトリのタスクだけ |

## 3. 役割分担

| 役割 | 受け持つこと |
|---|---|
| 利用者 | 依頼と段階の指定、判断と承認、リモートのリポジトリの作成・権限の付与、認証のやり直し |
| 親のセッション | 調査・設計・計画・統合・検証のやり直し・報告、状態の記録、**外部への公開操作**（承認のあと） |
| サブエージェント | 範囲のはっきりした実装・定型の繰り返し・文書への反映。自分の作業ツリーの中だけ。公開操作と指令リポジトリの書き換えはしない |
| 別の PC・別のエージェント | 担当していないタスクを読むだけ。空いているタスク（`ready`）を主張して進める |

モデルは、判断の要る作業を上位のモデル、定型の作業を軽いモデルに分ける。モデルごとに利用枠が別のことがあるので、片方が尽きたら、もう片方で進められるステップを先に進める。

## 4. 承認の境界

指令リポジトリの `policy.md` が正本。要点だけ挙げる。

- 段階（`stage`）が、進めてよい範囲を決める。途中で広げるときは、利用者に確かめて「決定事項」に記録する
- 段階に関わらず、個別の承認が要る操作がある（本流への直接の push・強制の push・削除・リリース・システムの設定・依存の追加・第三者の目に触れる書き込み・担当の引き継ぎ）
- 承認が要る操作は、計画の時点で書き出し、最後にまとめる。承認は、その操作だけに有効

## 5. 検証と報告

- 検証の方法は案件ごとに違うので、`project.md` の「検証の方法」に書く。キットは中身を持たない
- どの案件でも共通の基準
  - 機械的な一括の変更は、dry run → 件数と残りの確認 → 書き込み → 変更の前後の比較
  - サブエージェントの報告をうのみにせず、親が差分を読み、検証を流し直す
  - 確かめられないもの（実機・実時間・権限が要るもの）は、報告に必ず書く
- 報告の順: 結論 → 成果物 → 確かめたこと → 確かめられていないこと → 推測のままの点 → 利用者の判断が要ること → 訂正（`templates/report.md`）

## 6. 自動再開（auto-resume-global）との連携

1. 上限で止まると、`auto-resume-global` が解除時刻に PC を起こし、セッションを分岐して再開する
2. 再開の指示に足した案内（`install.ps1 -LinkAutoResume`）に従い、再開したセッションが `/auto-loop resume` を実行する（緊急のタスクがあれば先に行い、担当中のタスクが無ければ `/auto-loop next` で次を決める）
3. `resume` は、この PC の進行中の印と作業フォルダから、続きのタスクを決め、タスクファイルを読んで前提を確かめ直す

### 起動時・スリープ解除時の自動起動（任意）

`auto-resume-global` は、上限・再起動で**止まったセッション**しか再開しない。止まったセッションが無いときにも、起動時・スリープ解除時に着手・再開を始めさせたいときは、`install.ps1 -EnableKick` でタスク `AutoLoopKick` を登録する（Windows 専用）。

1. ログオン・スリープ復帰の 3 分後に `kick.ps1` が動く（`auto-resume-global` の巡回は 1 分後。先に再開を済ませさせる）。ほかに、`kick.intervalMinutes`（`-KickIntervalMinutes`）を決めればその分ごとに、週の上限の解除時刻が分かれば毎週その 6 分後に PC を起こして動く（タスク `AutoLoopKickWeekly`。解除時刻はセッションの記録から取るか、`kick.weeklyResetAt` で手で決める）
2. `kick.ps1` は、git とファイルだけで判断する（利用枠を使わない）。起こさないのは: `auto-resume-global` が無い・停止中 / 前に起こしたセッションが手を動かしている / 上限の解除待ち（復帰タスクが先の時刻に登録されている。または、セッションの記録に解除時刻が先の上限があり、そのあとに普通の応答が無い）/ ほかのセッションが手を動かしている（15 分の内に作業の記録がある。入力待ち・指示が無い・上限の解除待ちのセッションは数えない）/ 前に起こしてから 4 時間たっていない（週の解除時刻の起動では見ない）/ やることが無い
3. やること（担当中の `doing`・回答の届いた `waiting` / `blocked`・自分に合う `ready`・受付の未整理）があれば `work`、無ければ手が空いたときの作業（`idle`。24 時間に 1 回まで。定義がすべて実施済みなら起こさない）として、新しいウィンドウで `claude` を起こし、`/auto-loop next` を実行させる
4. 起こしたセッションは、記録が 60 分のあいだ書かれなければ終わらせる（対話のセッションは自分では終わらず、PC が眠れないため）。続きは、次に起こされたセッションがタスクファイルを読んで行う

判断と理由は `~/.claude/auto-loop/logs/auto-loop.log` の `[kick]` の行に残る。あわせて、指令リポジトリの `state/pcs/<ID>.json` に PC の状況（最後の判断・理由・手を動かしている / 止まっているセッションの数・次の復帰・週次の起動の時刻）が書かれる（自動起動を有効にした PC だけ。中身が変わったときか 60 分ごと）。数値は `config.json` の `kick` で変えられる（`references/setup.md`）。止めるときは `install.ps1 -NoCopy -DisableKick`。

分岐したセッションは ID が変わる。scratchpad も変わる。止まったサブエージェントに続きを頼めないことがある。いずれも、タスクファイルと `~/.claude/auto-loop/work/<タスク ID>/` と作業ツリーの実物から立て直す。

## 7. 既知の落とし穴

実際に起きたものを、技術に依存しない形でまとめた。案件に固有のものは、その案件の `project.md` の「落とし穴」に足す。

### 認証・権限・外部サービス

| 落とし穴 | 備え |
|---|---|
| 朝は有効だった認証が、夕方に切れている | 着手・再開・公開操作の直前に `preflight` |
| `!` で実行するコマンドは非対話。対話を前提にしたログインは失敗する | 直し方は `--web` などを付けた完全なコマンドで示す |
| push 先が削除予定・アーカイブ済みで、本流が別の場所に移っている | `preflight` が状態を見る。本流の場所は `project.md` に書く |
| リモートが複数あり、ローカルの基準ブランチが本流より大きく遅れている | 作業ブランチは `<本流リモート>/<基準ブランチ>` から切る |
| git ホストの有効なアカウントが、案件の指定と違う | `project.md` の「アカウント」と照らす。切り替えは利用者に確かめてから |
| 同じホストのアカウントが資格情報の保存先に複数あると、無人の git が「どれを使うか」の入力待ちで止まる（対話では選ぶ画面が出るので気づかない） | clone ごとに `git config credential.https://<ホスト>.username <アカウント>` で固定する。`preflight` が直し方を示す |
| PowerShell の `Set-Content -NoNewline` で git の出力（差分など）を書くと、行が改行なしでつながり、控えが使えなくなる | 差分は `git diff > ファイル` のように git に直接書かせ、`git apply --check` で当てられることを確かめてから元を消す |
| 過去のセッションの作業ツリーが、一時フォルダに大量に残る | `preflight` は変更の無いものを 1 行にまとめ、未コミットの変更があるものだけを挙げる。片付けは利用者に確かめてから |
| サブエージェントの公開操作は、権限の確認で止まる | 公開操作は親だけ |

### 中断と再開

| 落とし穴 | 備え |
|---|---|
| 並列のサブエージェントは、同じ枠を一気に使う。親も子も同時に止まる | 並列の数を抑える。上限の近くで大きな並列を始めない |
| 分岐したセッションから、元のサブエージェントに続きを頼めない | 委任を起動の前に記録する。作業ツリーの変更を「仕上げ」として引き継ぐ |
| scratchpad はセッションごと。分岐で見えなくなる | 再開をまたぐものは `work/<タスク ID>/` に置く |
| バックグラウンドの処理・ローカルのサーバーは、セッションと一緒に終わる | 「再開時に確かめ直す前提」に書いておき、再開のたびに確かめる |
| 「書いたつもり」のファイルが、権限の拒否で書けていない | 委任の前に、渡すファイルの存在を確かめる |
| 自動化が「何もしなかった」とき、理由が残っていないと原因を断定できない | 拒否・失敗・見送りを、理由と一緒にログに残す |

### 作業の進め方

| 落とし穴 | 備え |
|---|---|
| 件数や規模だけで判断して、提案が誤る | 根拠は代表例を実際に読んで確かめる。誤りは後の報告で訂正する |
| 見立てを事実のように示す | 推測には「推測」と書き、利用者の判断に回す |
| 一括置換の取り違え（正規表現の書き損じ、改行の変化） | dry run、件数と残りの確認、変更の前後の比較 |
| 行末・文字コードが、道具によって変わる | 編集は専用の道具で行い、変更後に種類を確かめる。出力の文字コードを明示する |
| 巨大なファイル・依存のフォルダを走査して、時間切れになる | 最初から除外する |
| 大文字・小文字だけが違うファイル名は、Windows では同じファイル | そういう名前の組を作らない（このキットの作成中に、`AGENTS.md` を別のファイルで上書きした） |
| スクリプトの中で、道具と同じ名前の関数を定義する（PowerShell は大文字・小文字を区別しない） | 外部の道具と同じ名前を関数に付けない（通し試験の作成中に、自分自身を呼び続けて止まらなくなった） |
| 似た名前の仕組みが 2 つあり、取り違える | スキル・フォルダ・タスク・ログの名前を、配布名にそろえる。改名は移行つきで行う |

## 8. グローバルの CLAUDE.md に足すと良い一文（任意）

直接頼まれた作業を取りこぼさず起票させたいとき、利用者が `~/.claude/CLAUDE.md` に足す。

```markdown
- 複数ステップに及ぶ作業（調査して提案、実装して PR・MR など）を頼まれたら、着手の前に `/auto-loop intake` で指令リポジトリに起票し、`/auto-loop start` の手順で進める。区切りごとに `/auto-loop checkpoint` する
```
