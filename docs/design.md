### 1.1 2 つのスキルの関係

| 決めたこと | 理由 |
|---|---|
| `auto-loop` と `auto-resume-global` は、1 つにまとめず別々に保つ（2026-11-19。検討の結果を利用者が採った） | 受け持ちが違う（`auto-resume-global` は指令リポジトリを知らず、単体で使える）。`auto-resume-global` の導入は、タスク スケジューラ・電源の設定・`settings.json` のフックを変える「要指示」の操作で、`auto-loop` の導入に混ぜると承認の境界が広がる。macOS・Copilot など、`auto-loop` の手順だけを使う場合もある |
| 正本は、どちらもこのキット。yzkn/skills は配布先（従）（2026-11-19。利用者の決定） | 2 つのつなぎ目を同じリポジトリの同じ PR で直せる。それまでは `auto-resume-global` だけ配布先が正本で、キットは複製だった（`skills/auto-resume-global/DISTRIBUTION.md`） |
| つなぎ目は、`auto-loop` → `auto-resume-global` の一方向だけ。下の表のものだけを読む・書く | `auto-resume-global` を `auto-loop` なしで使えるようにする。下の表に無いもの（`state/handled.json` など、`auto-resume-global` の中の状態）は読まない |

`auto-loop` が使う `auto-resume-global` のもの（インストール先は既定 `~/.claude/auto-resume-global/`。`auto-loop` の側は環境変数 `AUTO_LOOP_AUTO_RESUME_HOME` で替えられる）:

| もの | 使うところ | 使い方 |
|---|---|---|
| `config.json` があること | `kick.ps1`・`install.ps1 -EnableKick`・`preflight.ps1` | 無ければ「未導入」として、自動起動を見送る |
| `disabled` があること | `kick.ps1` | あれば「停止中」として、自動起動を見送る |
| `config.json` の `claudePath` | `kick-session.ps1` | 起こすセッションの `claude` の場所。無ければ PATH の `claude` |
| `config.json` の `shellPath`・`terminalPath` | `kick.ps1` | 新しいウィンドウを開くシェル・Windows Terminal。無ければ自分のシェル・PATH の `wt.exe` |
| `config.json` の `resumePrompt`・`rebootResumePrompt` | `install.ps1 -LinkAutoResume`（書く。控えを `~/.claude/auto-loop/state/` に残す）・`preflight.ps1`（読む） | 再開の指示の末尾に「`/auto-loop resume`（無ければ `next`）」の案内を足す。`preflight.ps1` は、指示に `auto-loop` の文字があるかを見る |
| タスク スケジューラのタスク `ClaudeAutoResumeGlobal-Wake` | `kick.ps1` | 次の実行時刻が先なら「上限の解除待ち」として、自動起動を見送る |
| `config.json` の `marginMinutes` | `kick.ps1`（`Find-PendingLimit`） | セッションの記録の上限の解除時刻に足す分（無ければ 3）。この時刻より前なら、復帰タスクが無くても見送る |
| 再開・復帰の遅れ（解除時刻の 3 分後、ログオン・復帰の 1 分後） | `install.ps1 -EnableKick`（タスクの遅れ） | `kick.ps1` をその後（ログオン・復帰の 3 分後、週の解除時刻の 6 分後）に動かし、先に再開を済ませさせる |

- このほか、セッションの記録（`~/.claude/projects/*/*.jsonl`）の上限の記録の読み方は、`auto-resume-global` と同じ考え方で `auto-loop` の `AutoLoop.psm1` にも別に書いている（コードは共有しない。記録の形は Claude Code のもので、どちらのスキルのものでもない）
- `auto-resume-global` で上の表のもの（キーの名前・意味・インストール先・タスクの名前・遅れ）を変えるときは、`auto-loop` の側も同じ PR で直す。`auto-resume-global` の `SKILL.md` の「auto-loop との関係」にも同じことを書いている
- `preflight.ps1` は、インストール先を `~/.claude/auto-resume-global/` に決め打ちしていて、`AUTO_LOOP_AUTO_RESUME_HOME` を見ない（2026-11-19 に気づいた。直すかは未定）

## 2. 指令リポジトリ

### なぜ別のリポジトリにするか

作業が GitHub / GitLab の複数のアカウント・複数のリポジトリに分かれるため、状態を作業対象のリポジトリの中（`.loop/` など）に置くと、案件を横断して見られない。PC ごとの `~/.claude/` に置くと、ほかの PC・ほかのエージェントから見えない。そこで、**全員が読み書きできる 1 つの git リポジトリ**を正本にした。git であれば、どのエージェントも特別な道具なしに扱え、履歴がそのまま監査の記録になる。

### 構成

```
inbox.md                     受付（人が追記する）
roster.md                    エージェントの名簿
policy.md                    承認の境界（全案件に共通）
AGENTS.md / CLAUDE.md        エージェント向けの決まり（道具に依存しない書き方）
templates/                   task / project / delegation / report
projects/<案件>/
  project.md                 リポジトリ・アカウント・本流・検証の方法・落とし穴
  tasks/<ID>.md              タスク = 状態ファイル
  archive/<ID>.md            完了・取りやめ
```

| 決めたこと | 理由 |
|---|---|
| 1 タスク 1 ファイル | 複数のエージェント・人が同時に書いても、別のタスクなら git が競合しない。1 つの大きな一覧にすると、全員が同じファイルを書き換える |
| タスクファイル = 状態ファイル | 依頼・決定・計画・現在地・委任・成果物・未確認を 1 か所で読める。再開のときに読むものが 1 つで済む（論点 6-1） |
| 形式は Markdown + 1 行ずつのフロントマター | 人が GitHub の画面（スマートフォンを含む）で読み書きできる。フロントマターを「キー: 値」の 1 行に限れば、YAML のライブラリなしに機械的に読める |
| ID は `<日付>-<短い名前>`。連番を使わない | 複数のエージェントが同時に起票しても重ならない。採番のための排他が要らない |
| 人の入口は `inbox.md` への追記 | 見出し 1 行で依頼できる。ひな形を写す・フロントマターを書く、という手間を人に求めない。整理はエージェントが行う |
| 人の割り込みはタスクファイルへの直接の書き込み | 質問への回答・方針の変更を、エージェントが動いていない間にも残せる。エージェントは次の同期で読む |
| 完了したら `archive/` に移す | `tasks/` を小さく保ち、一覧の走査を速くする |
| clone の場所は指令リポジトリに書かない（PC ごとの設定） | PC によって違う。指令リポジトリには、どの PC でも同じもの（ホスト・リポジトリ・アカウント・本流）だけを書く |
| 名簿のファイル名は `roster.md` | `agents.md` にすると、Windows（大文字・小文字を区別しない）で `AGENTS.md` と同じファイルになる。作成中に実際に上書きが起きた |

### 状態（`status`）と段階（`stage`）

- `status`: `draft` → `ready` → `doing` ⇄ `waiting` / `blocked` → `done` / `dropped`。人の対応が要るのは `waiting`（判断・承認）と `blocked`（外部の要因）だけにし、一覧で先頭に出す
- `stage`: `propose` / `implement` / `merge`。「提案だけ」「実装まで」「マージまで」を依頼の時点で明示する型（論点 6-7）。指定が無ければ、いちばん狭い `propose`。範囲の表は `policy.md`

## 3. 複数の PC・複数のエージェント

### エージェントの ID

`<PC>-<道具>[-<アカウントや用途>]`（例 `pc1-claude-main`、`pc1-copilot`）。PC ごとの `~/.claude/auto-loop/config.json` に持ち、同じ PC の別の道具は環境変数 `AUTO_LOOP_AGENT_ID` で差し替える。名簿（`roster.md`）で重複を防ぐ。

### 担当の調停（claim）

排他のためのサーバーを置かず、**git の push の先着**で決める。

1. 取り込む → タスクファイルの `claimed_by` が空であることを確かめる
2. `claimed_by` などを書き、そのファイルだけをコミットして push する
3. push が拒否されたら（先を越された）、自分のコミットを取り消し、取り込みから判定し直す

2 つのエージェントが同時に主張すると、同じ行（`claimed_by`）を書き換えるので、後から push した側は必ず拒否される。通し試験（`tests/smoke.ps1` の 4）で、push の直前に相手の主張を割り込ませて確かめている。

| 決めたこと | 理由 |
|---|---|
| 印（`heartbeat_at`）が古くても、自動では引き継がない | 上限の解除待ちは最長で数日ある。「止まっている」と「待っている」を印の古さだけでは区別できない。`stale` と表示するにとどめ、引き継ぎ（`takeover`）は利用者の指示があるときだけにした |
| 状態を送る前に、リモートの `claimed_by` を確かめる | 引き継がれたあとの元の担当が、気づかずに作業と記録を続けるのを防ぐ（終了コード 2「主張が失われている」） |
| 同じ PC の中では、進行中の印のセッションで担当を見分ける | `claimed_by` はエージェント ID 単位なので、同じ PC の 2 つのセッション（上限からの再開と自動起動）がどちらも「自分の担当の継続」として進めてしまった（2026-11-20、20261120-no-parallel-sessions）。印に `sessionId`・`pid`・`processStart`（Claude Code の `CLAUDE_CODE_SESSION_ID`・`CLAUDE_PID`）を書き、そのセッションが「生きて手を動かしている」（プロセスが生きていて、会話の記録が `working` / `stale`）間は、別のセッションの claim・heartbeat・release を終了コード 2 で止める。上限の解除待ち・入力待ち・終わったセッションからは、印を移して続けられる（フォークの再開が通る）。環境変数の無い道具は、いままでどおり |
| 指令リポジトリの git の操作を、PC の中で排他にする | 同じ clone で 2 つのセッションが同時に pull すると「Cannot rebase onto multiple branches」で失敗した（推測: 同時の fetch で FETCH_HEAD が混ざる）。名前付きミューテックス（`Local\auto-loop-control-<パスのハッシュ>`）を `Update-ControlRepo`・`Sync-ControlRepo`・`claim.ps1` の全体で取る |
| 競合したら取り消して報告する。強制の上書きをしない | 相手（別のエージェントか利用者）の書き込みを消さない。旧キットの「回避しない・報告する」と同じ考え方 |
| 認証の入力待ちで止まらない（`GIT_TERMINAL_PROMPT=0`） | 無人のときに入力待ちで止まると、原因が分からないまま時間が過ぎる。失敗として返し、直し方を示す |

### 利用枠

AI のアカウントが同じエージェントは、枠を分け合う。名簿に「AI のアカウント」を書き、同じアカウントのエージェントに同時に大きな作業をさせない（運用で守る。機械的には止めていない）。

### 着手の順

| 決めたこと | 理由 |
|---|---|
| 着手・再開のたびに、近傍のタスクの優先度を判定しなおす | 起票の順のまま進めると、あとから来た大事な依頼が待たされる。判定の材料（`priority`・回答の有無・古さ）は一覧から取れる |
| 担当中のタスクは続ける。先に行うのは `urgent` だけ | 切り替えのたびに前提の確かめ直しが要り、中途半端な作業ブランチが増える。割り込みの入口を 1 つに絞った |
| `urgent` に上げてよいのは利用者だけ | エージェントが自分の判断で割り込みを作ると、原則（続ける）が崩れる |
| 同じ PC では、同時には 1 つのリポジトリのタスクだけ | 複数のセッションが同時に大きな作業をすると、利用枠を使い切って全部が止まる。PC 単位にしたのは、同じ PC のエージェントは同じ利用者の枠を使うことが多く、名簿（PC の列）で確かめられるため。機械的には止めていない（`kick.ps1` が「ほかのセッションが動いていれば起こさない」だけ） |
| PC の状況は、指令リポジトリの `state/pcs/<ID>.json` に `kick.ps1` が書く。中身が変わったときか 60 分ごと。そのファイルだけをコミットし、ほかの変更が無いときだけ push する | ダッシュボード（参照だけ）が GitHub の API で読めるのは、指令リポジトリだけ。15 分ごとの起動のたびにコミットすると履歴が埋まる。`git add -A` の同期を使うと、同じ PC のほかのセッションが書きかけのタスクファイルを巻き込むので、パスを指定してコミットし、push は作業ツリーがきれいなときだけにした（残ったコミットは次の同期で送られる）。理由の文から手元のパス・フォルダ名を除く（利用者名を含むため） |
| 起動のきっかけに、一定間隔（既定は使わない）と、週の上限の解除時刻の週次を足した。週次だけ PC を起こし、間隔は起こさない | 週の上限が解けた直後は、止まっていた作業も手が空いたときの作業も進められる。解除の曜日・時刻はアカウントごとに決まり、記録の `resetsAt` に絶対時刻で残るので、曜日を決め打ちにせず記録から取る（手で決めることもできる）。間隔の起動は、人が席を外して入力待ちになったウィンドウを補うためで、PC を起こすほどではない。週次は解除時刻ちょうどにほかの起動と重ならないよう 6 分後（`auto-resume-global` の復帰と再開は 3 分後） |
| 上限の解除待ちは、復帰タスクに加えて、セッションの記録からも見る。解除時刻（`resetsAt`）が先の上限があり、そのあとにどのセッションにも普通の応答が無ければ見送る。170 時間の内に書かれた記録の末尾（4MB）だけを読む | 復帰タスクは、`auto-resume-global` の対象外のセッション・止まったウィンドウに入力して最後の記録が上限でなくなったとき・登録の失敗では作られず、手でスリープ解除すると上限中でも起こしてしまっていた。上限はアカウント単位なので、上限のあとの普通の応答は解除の印になる（利用者の判断、2026-11-20）。解除時刻の無い上限の記録は使わない（いつまで待つか分からないため。`auto-resume-global` の `fallbackWaitMinutes` の推定は持ち込まない）。170 時間は週の上限の最長 7 日 + 余裕。ファイル全体を読むと 440MB で 7 秒かかったので、末尾だけを読み、行はまとめて絞る（同じ量で約 4 秒） |
| 「動いている」セッションは、最後の会話の記録で数える。入力待ち・指示が無い・上限の解除待ち・長く書かれていないものは数えない | 記録が新しいかだけで数えると、入力待ちのまま開いているウィンドウ（人が席を外した・答え終わった）があるだけで、何時間も起こせない。止まっているセッションは枠を使っていないので、共倒れの心配が無い。長いツールの実行（試験など）で `busyMinutes` を超えると止まっているとみなしうるので、既定は 15 分にとどめ、サブエージェントの記録も見る |
| 手が空いたときの作業は、1 回に 1 件・委任なし・既定は提案だけ | 人が見ていない時間に、枠を使い切らない・変更を積み上げない。定義は受付に置き、消さずに `最終実施:` で間隔を見る（定義は繰り返し使うので、タスクにして消す受付の件とは分けた） |
| 自動起動（`kick.ps1`）は、判断をスクリプトで済ませてから起こす | 「やることがあるか」を調べるためにセッションを起こすと、それだけで枠を使う。git とファイルで分かることは先に調べ、見送った理由をログに残す |
| 自動起動は `auto-loop` の側に置き、`auto-resume-global` は変えない | `auto-resume-global` は「止まったセッションの再開」に絞ってあり、指令リポジトリを知らない。やることの有無の判断は指令リポジトリの知識が要る。`claudePath` などの場所だけを借りる |
| 起こしたセッションは、記録が書かれなくなったら終わらせる | 対話のセッションは自分では終わらない。開いたままだと PC が眠れず、次の起動時・スリープ解除時にも「動いている」と見て起こせない。状態はタスクファイルにあるので、終わらせてよい |

## 4. 材料の教訓との対応

| 材料 | 起きたこと | このキットでの扱い |
|---|---|---|
| 2・論点 6-3 | 分岐後、止まったサブエージェントを呼べない | 委任を**起動の前に**タスクファイルに記録する。再開のとき、作業ツリーの実物を見て「仕上げ」を新しいエージェントに任せる（`resume`・`delegate`、`templates/delegation.md` の「引き継ぎ」） |
| 10・11 | push の段階で認証切れ。`!` のコマンドが非対話で失敗 | `preflight.ps1` がトークンを実際に使って確かめ、直し方を**完全なコマンド**で示す |
| 12 | push 先が削除予定 | `preflight.ps1` が GitLab の削除予定・アーカイブ・権限を見る |
| 13 | サブエージェントの push・PR 作成が止められた | 外部への公開操作は親だけ（`SKILL.md` の遵守事項、指示書の禁止事項、`policy.md`） |
| 14 | リモートが 3 つ。ローカルの main が大きく遅れていた | `project.md` に本流のリモートと基準ブランチを書く。`preflight.ps1` が、本流のリモートの向き先と、ローカルの遅れを見る |
| 15 | 親と子が同時に上限 | 並列の数の上限（`maxParallel`）、委任の前に利用枠を確かめる手順。枠の残りは機械的に取れないので、利用者に確かめる |
| 16 | scratchpad が分岐で失われた | セッションに依存しない `~/.claude/auto-loop/work/<タスク ID>/` |
| 17 | 「読め」と指示したファイルが無かった | 委任の前に、渡すファイルの存在を親が確かめる（`delegate`） |
| 18 | 再開後、ローカルのサーバーが落ちていた | タスクファイルの「再開時に確かめ直す前提」と、`resume` の手順 |
| 20〜23 | 改行・文字コード・一括置換・巨大ファイル | 技術や OS に寄るものは `operations.md` の落とし穴に一般化して載せ、案件に固有のものは `project.md` の「落とし穴」に足す |
| 24・25 | 件数だけで判断した。見立てのまま提示した | 報告の型（確かめたこと / 推測のままの点 / 訂正）、`propose` の進め方 |
| 論点 6-1 | 状態の持ち方 | 2 章 |
| 論点 6-2 | 着手前の確認 | スクリプト（機械的に見られるもの）と手順（見られないもの）に分けた |

## 5. 旧キット（Claude-LoopEngineeringKit.old）から取り入れたもの・見送ったもの

| 取り入れた | 形 |
|---|---|
| 状態の要約をスクリプトで出し、全文を読まない（`/loop-status`） | `status.ps1` |
| 道具・認証を、エージェントを動かす前に確かめる（`/tool-check`、認証の失敗はループ全体を止める） | `preflight.ps1` |
| 回避しない・報告する（ロックや検出を、名前や場所を変えてすり抜けない） | 競合・担当の喪失・認証の失敗は、取り消して報告する |
| 指示の差し込みへの備え（Issue の書き手を限る） | 指示の出どころを、指令リポジトリと目の前の利用者に限る（`AGENTS.md`） |
| 半自動（push と マージを人に任せる）という段階 | `stage` |
| 「確認済みの点」と「動かして確かめる必要がある点」を分けて書く | README と [field-checks.md](field-checks.md) |

| 見送った | 理由 |
|---|---|
| スタックの定義・雛形・CI | 技術スタックに依存する |
| `claude -p` を回す orchestrator、予算の台帳 | 今回の対象は対話のセッション。無人のループは、指令リポジトリの `ready` のタスクを拾う形で後から載せられる |
| GitHub Projects をチケットの正本にする | GitHub に固定される。GitLab の案件・複数アカウントを横断できない |
| フックと OS ロックによるガバナンス | 対象のリポジトリごとに守るものが違う。ここでは承認の境界（`policy.md`）にとどめ、機械的な強制は案件の側で行う |

## 6. 未解決の論点

| 論点 | 現状 | 案 |
|---|---|---|
| 状態の記録を忘れる | 手順で求めているだけ。機械的には強制していない | Claude Code のフック（Stop や一定間隔）で、進行中の印があるのに印が古いときに注意を出す |
| 利用枠の残りが取れない | 利用者に確かめる | 上限に当たった時刻と直前の作業量を記録し、目安を作る（旧キットの較正の考え方） |
| 人がいるかどうか | 見ていない | 承認待ちに入ったときの通知（別のスキル・連携の役目） |
| Claude Code 以外のエージェントでの運用 | `AGENTS.md` の手順を git で行う、という想定だけ。実際には動かしていない | Copilot などで 1 件通し、取り違えやすい点を `AGENTS.md` に足す |
| 指令リポジトリの書き手の制限 | 共同作業者に限る、という運用だけ | 受付の差分の書き手（コミットの作者）を名簿と照らす |
| 無人のループ | 起動時・スリープ解除時だけ（`kick.ps1`。対話のセッションを起こす）。定期の起動は無い | 一定間隔でも起こす。長い処理の途中で「記録が書かれない」と見て終わらせてしまわないよう、見張りの条件を増やす |
| 1 台 1 リポジトリの強制 | 手順で求めているだけ。同じタスクの二重の進行は、進行中の印のセッションで止める（上の「決めたこと」）。別のリポジトリのタスクを並行して進めるのは、まだ止めていない | 着手（claim）の前に、同じ PC の印のうち、生きているセッションが別のリポジトリのタスクを持っていれば止める |
| macOS / Linux | 未検証 | `pwsh` があれば動く見込み（推測）。通し試験を流して確かめる |
